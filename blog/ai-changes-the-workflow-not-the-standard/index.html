AI Changes the Workflow, Not the Standard

February 2026

My issue is not that AI writes code. It’s that it can make it too easy to produce code without fully understanding the change, the system around it, or the cost of what is being added.

I learned to code before these tools existed, starting in 2014 with an intro class as a high school freshman. Progress was trial and error: read the error closely, change one thing, run it again. Getting unstuck meant stitching together half-relevant answers from Stack Overflow, old forum posts, and random blogs. It was slow, but it built habits I still depend on: patience, attention to detail, and the ability to work through a system I don’t fully understand yet. When I joined Bloomberg in 2021, coding turned out to be only one part of the job. The rest was reading other people’s code, reviewing changes, and debugging larger systems I didn’t write.

The first problem is visibility. AI collapses the distance between request and result. Code shows up quickly, often in large chunks, and engineers can lose sight of what changed, why it changed, what assumptions were made, and what might break somewhere else. The speed itself makes it harder to slow down and inspect. If you can’t explain why a change was made, what tradeoffs it introduced, or how it fits into the rest of the codebase, “it works” is not enough.

The second is hidden tech debt. Used carelessly, AI produces code that works locally, passes the immediate task, and looks plausible in a PR while quietly making the system worse. It duplicates logic that already exists, ignores patterns the codebase already uses, and introduces abstractions that don’t fit. AI often optimizes for completion, not coherence. It’s good at getting something over the finish line and much worse at asking whether the solution should look this way, or what it will cost the next person who works in the code.

Part of that is the human side. Once the feature works and the PR is out the door, it’s easy to ignore the redundancy, the awkward patterns, and the assumptions no one checked. The immediate win is visible. The long-term cost usually isn’t.

What worries me most is what over-reliance does to how engineers learn. It lets people make the immediate change without understanding the system they are changing. They can ship code without building the intuition to anticipate failure, reason through tradeoffs, or debug when something breaks. And something always breaks: assumptions fail, edge cases show up, traffic patterns shift. At that point the question is not whether you could generate the change. It is whether you understand the system well enough to fix it on a random Wednesday at 2AM. If an engineer can ship changes but cannot explain how the system works, that is not leverage. That is dependency.

None of this means rejecting AI. Engineers should learn what it is good at, where it actually helps, and where it should stop. It handles boilerplate and mundane work well, where most of the structure is the same and only a few details change, and it can write a solid first pass. It helps you navigate a large codebase and form a high-level picture of an unfamiliar stack, as long as you verify what it tells you. It also works as a thought partner: sanity-checking a design, asking what you might be missing, comparing options, or acting as a rubber duck while debugging.

It lowers the barrier to entry, too. Beginners spend less time completely stuck, and engineers move across unfamiliar languages, frameworks, and systems faster. That is a real advantage, but lowering the barrier is not the same as building deep understanding. People still have to learn to reason about what they are building. AI lowers friction and increases speed. The challenge is using that speed without letting it replace judgment.

Two principles shape how I use AI. First, use it to accelerate your work, not replace your understanding. Second, trust it enough to use it, and verify it enough to own it.

AI makes engineers faster. It can help plan, write code, review code, and handle repetitive work that does not need deep attention every time. But it does not change what makes someone a good engineer. The skills that mattered in 2021 still matter now: understanding systems, debugging carefully, reading code closely, reasoning about tradeoffs, and maintaining quality over time. The goal is to use AI in a way that makes judgment more effective, not less necessary.

Verifying it enough to own it means reading the code closely, testing it against actual behavior, and making sure it fits the system it is entering. In infrastructure or security-sensitive code, verification has to be stricter. “Mostly right” is not enough.

One rule follows from that: never merge code you cannot explain. If you can’t say what a change does, why it was written that way, what it assumes, and how it fits into the rest of the system, it should not ship. “The AI wrote it” does not change that. Ownership still belongs to the engineer.

That also means anchoring AI output to the actual codebase, not generic best practices. A generated solution can look clean in isolation and still be wrong for the system it is being added to. Ask specific questions: Does this match our architecture? Do we already have a utility or pattern for this? Is this the style we want here? Who is going to maintain this six months from now?

Used with care, AI can accelerate work and improve quality. But it only works when the engineer stays responsible for understanding, judgment, and ownership. AI changes the workflow. It does not change the standard.
